# Оптимизация Kadr: замеры и изменения

Первый этап — загрузка обложек; второй — большие библиотеки, карта и тир-лист.

## Что измерено

2026-10-20, MacBook Air, Apple Silicon, 8 ГиБ RAM, macOS 27.0, Xcode/Instruments 27.1.
Измерен **изолированный путь загрузки и CPU-отрисовки изображений**, а не весь интерфейс Kadr.
Сравниваются прежний `NSImage(contentsOf:)` и новый `CoverThumbnailLoader`.

Одинаковая Release-компиляция (`swiftc -O`), 96 синтетических JPEG 1067×1600,
24 одновременно удерживаемые обложки, вывод 480×720 пикселей (240×360 pt при 2×).
Каждая страница посещается дважды; в каждом запуске 576 загрузок/отрисовок.
Три независимых запуска каждого варианта, последовательно, без параллельных сборок и записи Instruments.
Под «повторным посещением» подразумевается повторная загрузка на уровне приложения;
файловый кэш macOS принудительно не сбрасывался.

Медианы трёх запусков:

| Метрика | Прежний путь | Новый путь |
| --- | ---: | ---: |
| Время всего сценария | 4922 мс | 2359 мс |
| P95 одной загрузки с отрисовкой | 13,20 мс | 7,95 мс |
| Максимальный RSS процесса бенчмарка | 128,6 МиБ | 115,8 МиБ |
| Расчётный пиксельный объём 24 источников (`bytesPerRow × height`) | 156,3 МиБ | 31,6 МиБ |

Пиксельный объём **не равен** фактически занятой RAM. RSS учитывает также AppKit,
ImageIO, кэш и временные объекты. Эти цифры нельзя переносить на память всего приложения
или интерпретировать как измерение FPS/скорости открытия экранов. Синтетические JPEG
не заменяют проверку на разнообразных настоящих изображениях.

## Instruments

Time Profiler исходного варианта: около 5,89 с CPU-сэмплов, почти все на главном потоке;
около 5,33 с — внутри CPU-отрисовки, включая CoreGraphics scaling/resampling.
Профиль записан отдельно от численных запусков. Десятисекундная запись остановила
долгий тестовый процесс по лимиту времени; данные Time Profiler проверены в GUI Instruments.
Первый совместный запуск Time Profiler/Allocations не подключился к процессу и не использован.
Для записи временный CLI получил отладочную подпись; entitlements/подпись Kadr не менялись.

В профиле нового загрузчика (отдельный более длинный сценарий, 12 повторов) тяжёлый стек
`CoverThumbnailLoader.decode` / AppleJPEG находится на рабочих потоках. Главный поток
занимает около 10,7% CPU-сэмплов этой записи. Это проверка размещения работы по потокам,
а не прямое сравнение абсолютных CPU-времён двух записей с разной длиной.

Записи первого прогона: `/private/tmp/kadr-performance.RExkU2/legacy-time.trace`
и `/private/tmp/kadr-performance.RExkU2/optimized-time.trace`.

## Что изменено

- ImageIO создаёт миниатюру под физический размер отображения с учётом ориентации и aspect-fill.
- Небольшие оригиналы не увеличиваются при декодировании; отображение по-прежнему пропорционально заполняет рамку.
- Размеры запросов округляются до 32 пикселей, чтобы не декодировать вариант на каждый пиксель ресайза.
- Отдельный actor последовательно выполняет чтение/декодирование вне главного актора.
- Общий LRU-кэш имеет лимит 48 МиБ по стоимости декодированных изображений.
  Лимит не включает изображения, удерживаемые экраном, и не является лимитом RSS приложения.
- Повторные одинаковые запросы используют кэш; отменённые запросы в очереди не декодируются.
- При memory pressure кэш очищается; при исчезновении постера его локальная ссылка освобождается.
- Дисковый кэш не создаётся, оригиналы не изменяются, SwiftData и формат резервных копий не меняются.

## Повторить

Из корня проекта:

```sh
bash scripts/benchmark-covers.sh
```

Скрипт создаёт только новую временную папку, печатает её путь и оставляет JSON для сравнения.
Он не запускает приложение через SwiftPM и не обращается к пользовательской медиатеке.
Перед замером закройте тяжёлые задачи и не запускайте параллельно Instruments или сборку.

Для проверки самого приложения используйте `Kadr.xcodeproj`, схему `Kadr`, Product → Profile.
Не используйте Debug для итоговых выводов о производительности.

Рендер-тесты используют настоящую синтетическую обложку в отдельном временном CoverStore.
Для ручной проверки можно запустить только `EducaScreenRenderingTests` через `xcodebuild test`,
добавив переменную `TEST_RUNNER_KADR_RENDER_PREVIEW=light-library-sidebar`:
выбранное окно с базой в памяти показывается на 60 секунд. Обычный запуск тестов окон не открывает.

## Проверки реализации

- Полный `xcodebuild test` проекта `Kadr.xcodeproj`, схема `Kadr`, macOS arm64,
  `CODE_SIGNING_ALLOWED=NO` — завершился с exit code 0.
- Восемь новых тестов проверяют Retina-размеры, ориентацию, aspect-fill,
  сохранность оригинала, повторные запросы, LRU-лимит, отмену и повреждённые файлы.
- Рендер-тесты обеих тем прошли с настоящей синтетической обложкой;
  PNG карточек/деталей и отдельное живое окно библиотеки просмотрены вручную.
- `bash -n scripts/benchmark-covers.sh` и `git diff --check` — без ошибок.

## Ограничения первого этапа

- Время запуска и первого содержательного кадра всего приложения.
- FPS/задержки реальной прокрутки, карты и анимаций.
- Большие UI-библиотеки тогда не проверялись; их изолированные замеры приведены ниже.
- Длительная работа и утечки.
- Эффект на размер релизного DMG: это не цель изменения загрузчика.

## Второй этап — большие библиотеки

2026-10-21, тот же MacBook Air, macOS 27.0, Xcode 27.1, Release arm64.
Проверены настоящие `LibraryView`, `GeographyView` и `TierListView` в окне 1080×760 pt.
В обоих вариантах уже используется загрузчик обложек первого этапа.
Никакие пользовательские записи и обложки не используются.

### Стенд и границы замера

- SwiftData только в памяти: 100, 1000 и 5000 фильмов/сериалов с длинными русскими названиями.
  80% просмотрены, часть без оценки/страны/тира; совместное производство сохранено.
- 96 разных файлов синтетических JPEG, повторно используемых записями. Разнообразие
  настоящих постеров, дисковые fault/fetch и холодный запуск этим не моделируются.
- Каждый процесс проходит библиотеку → карту → тир-лист, закрывая окно между этапами.
  Контейнер, системные кэши и общий кэш миниатюр сохраняются в пределах процесса.
- `initial_layout_ms` — создание окна и первая принудительная раскладка, а не момент
  готовности всех обложек, первый GPU-кадр или время запуска установленного приложения.
- `footprint_bytes` — physical footprint **всего тестового процесса** (`TASK_VM_INFO`)
  в конце этапа, включая базу, тестовый раннер и предыдущие экраны. Это не пик RAM,
  не RSS из первого бенчмарка и не прогноз памяти любой реальной медиатеки.
- 24 программных шага вертикальной прокрутки туда/обратно, до 6000 pt. Время шага
  включает раскладку, паузу 16 мс и задержку возобновления на главном акторе.
  P95 этого времени — диагностическая метрика, **не FPS и не GPU frame time**.
  На карте автоматический сценарий прокручивает внешний экран; внутренний список
  страны дополнительно проверен вручную.
- Для 100/1000 — по одному контрольному запуску, для 5000 — медианы трёх независимых
  запусков каждого варианта. Все численные прогоны последовательны, без Instruments
  и параллельных сборок. Профилировочные/ручные запуски в таблицы не включены.

### Причины и исправления

Time Profiler подтвердил большую работу на главном потоке: у карты — раскладка
SwiftUI и создание/обновление display list и слоёв; у тир-листа — повторные вызовы
`tierLane` и чтения `Movie.tierRawValue` при фильтрации всей коллекции.
Записи проверены в GUI Instruments:
`/private/tmp/kadr-library-perf.NFDglo/baseline-map.trace` и `baseline-tiers.trace`.
Временная отладочная подпись применялась только к тестовому `.app`, настройки подписи
и entitlements проекта не менялись.

Исправлено:

- Списки фильмов страны и записей без стран используют `LazyVStack`:
  строки вне видимой области больше не создаются все сразу.
- Тир-лист группирует записи одним проходом вместо повторной фильтрации для каждой категории.
  Состав групп не кэшируется между изменениями моделей: перемещение и редактирование остаются реактивными.
- Геометрия бликов хранится в отдельном `SidebarReflectionState`.
  Её наблюдает только фон сайдбара, а не весь `LibraryView` с фильтрами и тир-листом.
  Цвета, сами блики, жесты и настройки доступности не изменены.

### Проверки и воспроизведение

`GeographyListLoadingTests` на прежнем варианте воспроизвёл регрессию:
в маленькой панели декодировались все 100 уникальных обложек. На исправленном варианте
тест проходит, требуя реальную загрузку видимых обложек и меньше 50 декодирований.
Полный `xcodebuild test` в Release прошёл с exit code 0. Обычная Release-сборка
без `KADR_ISOLATED_TEST_HOST` также завершилась с exit code 0 (сборка без запуска).
Рендер-тесты проверили обе темы,
цвета категорий и наличие бликов. PNG карты и тир-листа просмотрены вручную.
В живом окне на 5000 записей проверены прокрутка страны с 1778 фильмами,
открытие фильма после прокрутки, Escape, наличие цветов и мягких бликов тир-листа.

Повторить измерения (девять последовательных запусков, результаты JSON и логи во временной папке):

```sh
bash scripts/benchmark-library.sh
```

Скрипт включает `KADR_ISOLATED_TEST_HOST`: даже стартовое окно приложения получает
базу в памяти, а очистка пользовательской папки обложек в такой сборке не выполняется.
Это **только специальная тестовая сборка**, не сборка для установки или публикации.
Без этого явного флага поведение обычного приложения не меняется.
Нагрузочный тест выключен при обычном запуске тестов; для него нужны переменные
`TEST_RUNNER_KADR_PERFORMANCE_COUNT` и флаг компиляции из скрипта.
`TEST_RUNNER_KADR_PERFORMANCE_OUTPUT` задаёт путь JSON, а необязательная
`TEST_RUNNER_KADR_PERFORMANCE_PAUSE=map` или `tiers` оставляет выбранное окно на 30 секунд
для ручной проверки/подключения Instruments. Такие запуски не смешивайте с контрольными.

Сырые контрольные результаты текущего сравнения:
`/private/tmp/kadr-library-perf.NFDglo/{baseline,optimized}-{100,1000,5000}-*.json`.
`bash -n` обоих бенчмарк-скриптов и `git diff --check` выполнены без ошибок.

Далее остаются холодный запуск и дисковая база, длительные циклы/утечки,
реальные frame-time/FPS и горизонтальная прокрутка/drag-and-drop под нагрузкой.
Размер релизного DMG на этом этапе не уменьшался; зависимости, архитектуры,
подпись и настройки обновлений не менялись.

После этих замеров блики сначала приглушались, затем по запросу пользователя полностью
удалены вместе с `SidebarReflectionState`, сбором геометрии и рендерингом свечения.
Нативный материал сайдбара сохранён. Числа тир-листа выше относятся к варианту
до этих визуальных правок; дополнительный выигрыш от удаления эффекта не измерялся.
